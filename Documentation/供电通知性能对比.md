# 供电通知优化：修改前后与性能影响

测量日期：2026-11-05。本轮仅核对代码和只读测量，未修改运行策略或应用代码。

## 执行路径

| 项目 | 修改前 | 修改后 | 性能与耗电影响 |
| --- | --- | --- | --- |
| 供电监听 | 通用电量更新、IOKit 系统事件、热状态事件 | 额外增加供电切换专用事件 | 主程序和辅助组件各增加一个被动 RunLoop 来源，无事件时不按时间轮询 |
| 提交通知前 | 转入主线程任务，读取完整电源快照后判断变化 | 回调直接读取轻量供电与热状态，优先判断和通知 | 缩短通知前关键路径，减少主线程排队；不保证系统会更早上报事件 |
| 完整状态读取 | 主线程读取；同一电源事件通常先读一次，再由 refresh 读取一次 | 完整读取转后台，待办事件合并后刷新 | 减少重复读取和主线程占用；后台任务本身仍有调度开销 |
| 查询／操作正忙 | 这次刷新会直接返回 | 保留待办，忙碌期间每 50 毫秒检查一次，忙完补查 | 临时最多约 20 次等待唤醒／秒；没有待办时此任务结束，不是常驻轮询 |
| 重复／旧数据 | 按供电变化去重 | 增加供电和热状态时间戳过滤 | 增加少量比较和状态存储，防止旧回执重新触发提醒 |
| 计时日志 | 通知回执转到主线程后记录 | 在通知系统回调中增加提交耗时记录 | 每次通知和特定系统事件增加少量日志，便于分段定位延迟 |

原有 15 秒会话续租、打开面板时的每秒数字更新、定时截止检查、保活断言和实际显示／睡眠策略没有在本次通知优化中改变。新增事件可能使同一次插拔从两个通道到达，去重与合并减少重复通知和刷新，但不能据此保证所有情况下总 CPU 用量都下降。

## 关键读取路径微基准

直接调用生产代码，以 `-Osize` 编译；预热 20 次，两条路径交替测量各 500 次。没有插拔电源，也没有发送额外通知。

| 每次调用 | 修改前：完整快照 | 修改后：快速供电＋热状态 |
| --- | ---: | ---: |
| 墙钟耗时中位数 | 115.792 微秒 | 50.250 微秒 |
| 墙钟耗时 P95 | 166.125 微秒 | 102.417 微秒 |
| 墙钟耗时平均值 | 114.243 微秒 | 56.898 微秒 |
| CPU 时间平均值 | 54.560 微秒 | 14.240 微秒 |

该样本中，通知前读取的中位耗时约减少 57%，CPU 时间约减少 74%。这些百分比仅适用于这两条读取路径。完整快照仍会在后台读取，测量也未包含后台调度、界面刷新、事件数量、通知系统或硬件上报过程，不能将上述百分比当作整个应用的 CPU 或耗电降幅。

两条读取路径正常情况下均低于一毫秒。因此，用户观察到的约一秒延迟不能仅用完整快照读取来解释。本次能够确认的改进是减少主线程等待风险、避免忙碌期间遗漏事件刷新；尚未证明真实拔线到横幅出现的总耗时缩短了多少。

## 耗电影响结论与边界

从执行方式推断，静置时新增开销应较小：没有新增常驻进程、持续短间隔采样或新的保活要求。事件到达时新增轻量判断和日志，完整读取的合并可能节省工作；请求正忙且有事件待处理时，会产生短时间的 50 毫秒等待唤醒。这些都需要与具体事件频率结合看待，不能承诺耗电绝对不变。

本轮没有修改前后同条件的长时间电量／能耗 A/B，也未执行真实插拔，所以没有每小时额外耗电百分比或瓦数结论。运行策略要求保持系统或内屏工作所带来的耗电仍然存在。
