# 供电通知延迟优化验证

日期：2026-11-05。

## 检查结论

历史日志中，应用检测到断电至通知提交成功约 18–28 毫秒，手动结束约 3–8 毫秒。这些日志未记录实际拔线时刻或系统横幅出现时刻，不能据此断言用户感知的一秒全部来自某一环节。

旧实现主要监听通用电量信息，回调再派发任务、读取完整电源快照。另一处确认的问题是：有查询或操作进行中时，电源事件发起的刷新会直接返回，可能延后保护结果的同步。

## 最终改动

- 增加 `IOPSCreateLimitedPowerNotification` 供电切换事件，保留原有通用电量、IOKit 与热状态监听；各通道共用去重逻辑。
- 主线程上的事件回调直接检查 `IOPSGetTimeRemainingEstimate` 公布的供电状态，取得有效切换后优先提交通知。未知读数保持未知，随后由完整快照补充，不猜测断电。
- 完整电源快照读取转入后台任务，避免同步 powerd 数据读取占用主线程；外部断言诊断仍在会话状态回执之后进行。
- 升温提醒先处理当前本地热状态，不以完整电源读取或 XPC 查询作为发送前提；因低电量、过热等原因结束会话仍等待辅助组件确认。
- 对忙碌／查询期间的电源刷新保留待办，并合并重复事件；在途刷新收到新事件后再补查一次。仅存在待办且被阻塞时短暂等待，不增加常驻轮询。
- 供电读数带时间戳，较旧的辅助组件回执不能把已断开的状态重新改为接电、进而产生重复提醒。热状态也过滤旧样本。
- 增加 `power.signal supply`、`power.signal thermal` 与 `notification.submit … accepted=… latency_ms=…` 日志。通知提交耗时在系统回调中直接记录，避免主线程刷新时间混入测量；该回执只表示系统接受提交，不代表横幅已经出现。

API 依据：[Apple IOPowerSources.h](https://raw.githubusercontent.com/apple-oss-distributions/IOKitUser/main/ps.subproj/IOPowerSources.h)、[Apple IOPowerSources.c](https://raw.githubusercontent.com/apple-oss-distributions/IOKitUser/main/ps.subproj/IOPowerSources.c)。本机 Xcode SDK 头文件也已核对。专用监听不构成系统上报速度的保证。

## 验证与限制

- 59 项隔离测试通过：新增快速读数的未知值处理、旧回执去重、忙碌事件合并、在途刷新再次收到事件等检查。原会话与保护测试继续通过。
- Debug、Release 最终构建通过，正式版原位更新，启动取得正常辅助组件回执。
- 本轮实际手动结束通知：16:05:49.792 主程序确认结束，16:05:49.794 系统接受提交；提交调用至回调计时约 1.909 毫秒。后续主线程事件记录为 16:05:49.798，说明原事件日志还包含主线程排队时间。
- 用户暂不方便接电，按用户要求跳过本轮真实插拔。只读探针已退出；不能报告断电体感已经缩短到某个数值，也未做物理高温测试。
- 最终恢复策略 2「合盖熄屏，持续运行」，时长「直到手动结束」；电池供电，组件已连接、错误为无。
- 最新 DMG 3,429,399 字节，ZIP 2,855,565 字节，校验和通过。仅保留固定正式版及 Xcode 开发版。
- 使用手册已同步，原未测清单保留。

后续自行插拔若仍有延迟，可结合 `power.signal`、`event.power`、`notification.submit` 与横幅实际出现时间继续区分系统事件上报、应用处理和系统展示三段。
